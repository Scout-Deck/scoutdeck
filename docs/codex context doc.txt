### Database structure

The current database maps to the application schemas as follows:

- `profiles` → `Profile`
  - One profile row per Supabase Auth user.
  - Uses the authenticated user's `user_id`.

- `opportunities` → `Opportunity`
  - Stores opportunities.
  - `Eligibility` from the original API schema has been flattened into queryable columns such as `education_level`, `experience`, etc.

- `saved_opportunities`
  - Stores the relationship between a user and an opportunity.
  - `isSaved` is NOT stored on `opportunities`.
  - `isSaved` should be derived per request based on the current authenticated user and `saved_opportunities`.

The SQL schema/policies are provided in the attached SQL file.

### Auth decisions

Supabase Auth is being used for the MVP.

The database is designed around:

`auth.users.id → profiles.user_id`

RLS policies assume users can only access/edit their own user-specific data.

The original API did not have an authentication/user concept. That has now been added.

## Application flow being implemented

The intended MVP flow is:

1. User signs up/logs in with Supabase Auth.
2. Supabase creates the authenticated user.
3. A corresponding `profiles` row is created/updated.
4. User submits their information through the profile/onboarding form.
5. Profile data is stored in Supabase.
6. The stored profile information is provided to the AI API.
7. AI uses the profile information to find/rank/generate relevant opportunities.
8. Opportunities are stored in `opportunities`.
9. Users can save/unsave opportunities through `saved_opportunities`.
10. `isSaved` is computed from the relationship rather than stored as an opportunity field.
